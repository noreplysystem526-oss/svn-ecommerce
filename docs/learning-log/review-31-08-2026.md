## 3. Kiến trúc tổng thể — không có tầng "API"

Điểm khác với mô hình client-server truyền thống: **không có REST/route.ts nào đứng giữa frontend và DB.**

```
Server/Client Component
        │
        ▼
Supabase JS client (gọi thẳng, không qua fetch("/api/..."))
        │
        ▼
Postgres (Supabase)
```

"API" thực chất là các **Server Actions** — hàm `"use server"` chạy trên server nhưng được gọi trực tiếp như hàm JS từ Client Component (Next.js tự đóng gói thành network call ẩn).

### 3.1 Vì sao có 2 (thực ra 3) kiểu Supabase client

| File | Dùng `createServerClient`/`createBrowserClient` | Chạy ở đâu | Vì sao cần tách riêng |
|---|---|---|---|
| `lib/supabase/client.ts` | `createBrowserClient` | Client Component | Không có quyền truy cập `next/headers` (cookie server-side) |
| `lib/supabase/server.ts` | `createServerClient` | Server Component / Server Action | Đọc/ghi cookie qua `cookies()` từ `next/headers` để duy trì session giữa các request |
| `lib/supabase/middleware.ts` | `createServerClient` | Middleware (`updateSession()`) | Middleware chạy trước khi request tới route, cần tự quản request/response cookie thủ công (không dùng được `next/headers`) |

**Khái niệm cốt lõi:** session Supabase được lưu trong cookie, mỗi runtime context (browser / server component / middleware) có API đọc-ghi cookie khác nhau ⇒ Supabase SSR yêu cầu 3 cách khởi tạo client khác nhau cho cùng một việc "kết nối DB".

**Lỗ hổng hiện tại:** không có file `middleware.ts` ở root gọi `updateSession()` ⇒ cơ chế refresh session **chưa được nối vào request pipeline** dù helper đã viết sẵn.

## 4. Pipeline tầng dữ liệu (data layer) — khái niệm chính của dự án

```
database.types.ts (Supabase generate)
        ↓
types/database.ts        — alias Row/Insert/Update mỗi bảng, ví dụ:
                            type Product = Database["public"]["Tables"]["products"]["Row"]
        ↓
lib/repository/*.ts      — query Supabase thô (SELECT/INSERT/UPDATE/DELETE), KHÔNG validate
        ↓
lib/validation/*.schema.ts — Zod schema, validate input trước khi ghi, export FormValues = z.infer<schema>
        ↓
lib/resources/*.config.ts — khai báo field (name/label/type) mỗi resource — metadata để SINH UI tự động
        ↓
lib/resources/index.ts    — gom config lại thành 1 map `resourceConfig`, export union type `ResourceName`
        ↓
lib/actions/*.actions.ts  — "use server", gọi repository (đây là nơi mutation thật sự chạy)
        ↓
UI: page.tsx / DataTable / ResourceForm
```

**Khái niệm học được ở đây — "config-driven UI" / "metadata-driven form":** thay vì viết 1 form/table riêng cho mỗi entity (product form, category form, order form...), định nghĩa field một lần dưới dạng data (`ResourceConfig`), rồi có 1 component `DynamicField`/`ResourceForm` chung đọc config đó để tự render field tương ứng. Đây là ý tưởng đằng sau `lib/resources/types.ts` (`FieldType`: `text | number | select | media | relation | rich_text`).

**Repository pattern:** tách logic truy vấn DB thô ra khỏi UI và khỏi action — repository không biết gì về validation hay HTTP, chỉ biết query. Action là lớp gọi repository + (đáng ra) validate bằng Zod trước khi gọi.

**Quan sát:** hiện tại các `*.actions.ts` mới (`lib/actions/product.actions.ts`, `order.actions.ts`, `category.actions.ts`) gọi thẳng repository, **chưa thấy bước validate bằng Zod schema trước khi insert/update** — tức tầng validation đã được định nghĩa (`lib/validation/*.schema.ts`) nhưng chưa được "gắn dây" vào action.

## 5. Route groups — cách Next.js App Router tổ chức 3 module

- `(auth)` — nhóm route không hiện trong URL (dấu ngoặc đơn = route group, chỉ để tổ chức code + share layout riêng), gồm `login`, `register`.
- `(shop)` — storefront: `page.tsx` (home), `products`, `products/[slug]`, `cart`, `checkout`, `account/*`.
- `admin` — không phải route group (không ngoặc đơn) vì `/admin` thực sự xuất hiện trong URL. Có layout riêng dùng `SidebarProvider` (shadcn sidebar pattern).

**Khái niệm:** route group cho phép nhiều layout gốc khác nhau cho các nhánh URL khác nhau mà không ảnh hưởng path — `(auth)/login` render ra URL `/login`, không phải `/auth/login`.

## 7. Nợ kỹ thuật / điểm cần lưu ý đã phát hiện

1. `admin/products/[id]/page.tsx`, `admin/products/components/product-form.tsx` (được `new/page.tsx` import sai path) — sẽ throw lỗi runtime nếu điều hướng tới.
2. Chưa có root `middleware.ts` gọi `updateSession()` — session Supabase không được refresh tự động giữa các request.
3. Actions mới (`lib/actions/*.actions.ts`) chưa gọi Zod schema (`lib/validation/*.schema.ts`) trước khi insert/update — validate hiện chưa thực sự chặn dữ liệu sai ở tầng server.
4. `Customers` chưa có tầng data riêng (không rõ dùng chung bảng `profiles` hay bảng riêng).
5. Toàn bộ storefront (`(shop)`) và `(auth)` là scaffold rỗng — chưa có tính năng khách hàng nào chạy được (browse, cart, checkout, login).
6. `@dnd-kit` đã cài nhưng chưa thấy nơi sử dụng.
